# Server

The server is a modular-monolith Go application built on go-zero. The runnable process is `server/apps/app-api`; reusable platform capabilities live under `server/platform`, technical infrastructure under `server/foundation`, and Fair Doudizhu product code under `server/business/doudizhu`.

## Server v1

The completed server v1 provides:

- liveness, readiness, standard response envelopes, request IDs, access logging, panic recovery, CORS, security headers, and body limits;
- MySQL and Redis lifecycle, deterministic current schema, caching, and integration tests;
- identity accounts, password credentials, authentication, rotating Redis sessions, and logout;
- Casbin/MySQL authorization, clustered policy synchronization, Admin APIs, audit, and one-time bootstrap;
- authenticated HTTP and WebSocket transports;
- Fair Doudizhu rooms, fairness, deterministic game rules, lifecycle supervision, settlement, persistence, final evidence, realtime participant delivery, and reconnect;
- Prometheus metrics and production deployment baselines.

The recommended starting point is `docs/operations/server-v1-release.md`.

## Prerequisites

- Go 1.25.8
- goctl 1.10.1
- Docker with Docker Compose

Install goctl:

```bash
go install github.com/zeromicro/go-zero/tools/goctl@v1.10.1
```

## Local startup

From the repository root:

```bash
make deps-reset
make schema-apply
make seed-apply
make run
```

The committed local configuration keeps Fair Doudizhu disabled. To run the complete server v1 locally, generate temporary development-only reveal and encryption keys in the same shell before `make run`:

```bash
eval "$(cd server && go run ./foundation/revealkeys/cmd/local-env)"
make run
```

The generator writes nothing to the repository. Its reveal key expires after 24 hours and must never be treated as production key management.

Verify the process:

```bash
curl -sS http://127.0.0.1:8888/health/live
curl -sS http://127.0.0.1:8888/health/ready
curl -sS http://127.0.0.1:8888/metrics | head
```

Stop dependencies:

```bash
make deps-down
```

## Structure

- `apps/app-api` — process entrypoint, configuration, bootstrap, HTTP and WSS composition
- `foundation/apperrors` — reusable application errors
- `foundation/cache` — Redis lifecycle and model caching
- `foundation/database` — MySQL lifecycle and transaction execution
- `foundation/httpmiddleware` — request IDs, access logging, recovery, CORS, headers, and body limits
- `foundation/response` — standard response envelopes
- `foundation/secureenvelope` — RFC 9180 HPKE opener
- `foundation/revealkeys` — reveal-key registry, lifecycle, signed manifests, and local development generator
- `platform/identity` — accounts and password credentials
- `platform/authn` — access tokens and rotating Redis sessions
- `platform/authz` — Casbin authorization and clustered synchronization
- `platform/admin` — administration and audit application services
- `platform/realtime` — authenticated bounded WebSocket hub
- `business/doudizhu/domain` — rooms, hands, cards, shuffle, bidding, play, scoring, and settlement rules
- `business/doudizhu/application` — command protocol, idempotency, sequencing, lifecycle, and final evidence
- `business/doudizhu/infrastructure` — MySQL persistence, secure contribution handling, live runtime, archive, and adapters
- `database/schema/current.sql` — complete current schema
- `database/seed/development.sql` — optional non-production development seed

## Authentication and administration

Authentication routes:

```text
POST /auth/login
POST /auth/refresh
GET  /auth/session
POST /auth/logout
```

The first administrator is created through:

```text
GET  /admin/bootstrap/status
POST /admin/bootstrap
```

Bootstrap creation requires `X-Admin-Bootstrap-Token`, is available only while the configured token exists, and closes after a `platform_super_admin` account exists. Remove `APP_ADMIN_BOOTSTRAP_TOKEN` and restart production containers after bootstrap.

Account, role, resource, session, audit, authorization-engine, and system routes are documented in `docs/api/admin.md`.

## Fair Doudizhu HTTP API

When `Doudizhu.Enabled` is true, authenticated accounts can use:

```text
POST /v1/doudizhu/commands
GET  /v1/doudizhu/hands/:handId/public
GET  /v1/doudizhu/hands/:handId/private
GET  /v1/doudizhu/hands/:handId/evidence
```

The HTTP command transport accepts the version `doudizhu-api-command-v1` and these types:

```text
room.create
room.join
room.leave
room.ready
room.hand.start
hand.commit
hand.reveal
hand.beacon
hand.dealt
hand.bid
hand.play
hand.pass
hand.cancel
```

The actor always comes from the authenticated session. The client cannot provide a trusted account, owner, role, permission, or seat.

See:

- `docs/operations/server-v1-release.md` for an end-to-end integration path;
- `docs/api/fair-doudizhu-protocol-v1.md` for the durable business protocol;
- `docs/api/fair-doudizhu-application-v1.md` for application and persistence behavior.

## Realtime API

The default authenticated WebSocket endpoint is:

```text
/ws
```

Game-specific message types are:

```text
doudizhu.command
doudizhu.hand.sync
doudizhu.command.result
doudizhu.hand.changed
doudizhu.hand.snapshot
doudizhu.hand.evidence
doudizhu.error
```

HTTP and WSS share one dispatcher and replay policy. Private cards are delivered only through account-targeted snapshots. Reconnect returns the caller's latest private snapshot, `notModified=true`, or immutable terminal evidence.

See `docs/architecture/doudizhu-realtime-v1.md` and `docs/operations/realtime-websocket.md`.

## Doudizhu configuration

Doudizhu is disabled by default. Enabling it requires authentication, reveal keys, and all of the following values:

```text
APP_REVEAL_KEYS_ENABLED=true
APP_REVEAL_KEYS_STATIC_JSON=<strict registry JSON containing private key material>
APP_DOUDIZHU_ENABLED=true
APP_DOUDIZHU_BEACON_PROVIDER=<provider identifier>
APP_DOUDIZHU_BEACON_ROUND=<round identifier>
APP_DOUDIZHU_BEACON_PROOF_SECRET=<at least 32 characters>
APP_DOUDIZHU_CONTRIBUTION_KEY_ID=<key identifier>
APP_DOUDIZHU_CONTRIBUTION_KEY_HEX=<64 lowercase hex characters>
```

Optional timeout and replay defaults are:

```text
BiddingTimeout: 45s
PlayingTimeout: 60s
SweepInterval: 1s
CommandTTL: 1m
ReplayTTL: 2m
ReplayEntries: 4096
```

`APP_REVEAL_KEYS_STATIC_JSON`, the beacon-proof secret, and the contribution key are sensitive. Do not commit, log, bake into an image, or expose them through configuration diagnostics.

## Production deployment

The supported single-host entrypoint is:

```bash
make production-config
make production-up
make production-down
```

The base production stack keeps plaintext HTTP/WS ports bound to loopback. Public traffic must use HTTPS/WSS through the optional TLS edge or an environment-specific ingress/gateway.

See `docs/operations/production-deployment.md` for required secrets, Compose project/data continuity, TLS, Kubernetes, probes, metrics, and environment overrides.

## Persistence and process boundary

MySQL owns durable identity, authorization, room/fairness state, command results, sequences, events, encrypted contribution references, and immutable terminal archives. Redis owns sessions, ordinary model cache entries, and authorization synchronization. Redis does not store active cards or live snapshots.

Active bids, cards, turns, passes, and live versions are authoritative in one running API process. Therefore server v1 supports reconnect to the same process and terminal evidence recovery, but not active-hand restoration after a process crash or transparent active-game migration between API replicas.

A future multi-instance game version must define authoritative room ownership, cross-node routing, and recoverable active state explicitly.

## Schema policy

- `server/database/schema/current.sql` is the complete current schema.
- Incremental migration history is intentionally not committed during this early phase.
- Temporary upgrade SQL must not be committed.
- Apply schema changes before starting API instances that require them.
