## Goal

Implement the first *verified* cross-platform Cocos client foundation with a small reusable TypeScript core/port seam and separate Web, WeChat Mini Game and mainland Douyin Mini Game adapters/build targets, without changing the existing Go server or business rules.

## Deliverables

1. Audit actual Cocos 3.8 project layout, current build scripts and SDK/tool availability; preserve code-first scenes and existing code.
2. Introduce minimal pure TypeScript client-core and Doudizhu-specific boundaries as justified by working code; platform interfaces/adapters for Web, WeChat, Douyin with runtime capability checks. Keep Cocos and platform SDK imports out of shared core.
3. Implement a minimal but working landscape entry shell and lifecycle for each supported build target, with safe-area/resizing checks. No invented production APIs or false game completion claims.
4. Reuse existing HPKE package and verify secure random source capability for each target. Never use `Math.random` as secret entropy. Fail closed when secure random is missing.
5. Validate transport authentication capabilities across platforms against existing WebSocket contract; if a platform cannot support the secure handshake, document a specific future server-side ticket contract rather than weaken security in this goal.
6. Automated contract/dependency tests and the strongest available Creator/target build and runtime smoke tests, clearly labeling simulator, developer-tool and real-device coverage.
7. Update docs with actual paths, commands, verified results and blockers; CI, self-review, archive/reset current on full acceptance.

##### Reproducible defects — ChatGPT fix ownership

- **P1-01 — Old send failure erases a same-ID retry and leaks its Promise.** Location: `clients/fair-doudizhu-cocos/assets/scripts/game/GameClientShell.ts:134-139`. Cause: asynchronous `send().catch` looks up by requestId without checking connection generation or pending-entry identity, then rejects its old closure. Reproduce: keep connection A's SDK send pending; reconnect to B (A's command is rejected as unknown); retry the identical requestId on B; reject A's old send; deliver B's valid correlated result. Expected: B resolves and its own timeout remains effective until settlement. Actual: A's callback clears B's timer and map entry, while B stays pending even after its valid response; disposal cannot find it either. Impact: reconnect recovery can hang indefinitely and retain caller work. Fix direction: bind each callback/timer to its exact pending object and generation; never delete or settle a replacement entry. First adversarial test reproduces this deterministically.
- **P2-01 — Explicit Go rejection is not correlated to the waiting command.** Location: `GameClientShell.ts:78-79`. Reproduce: submit a command, then deliver the actual versioned `doudizhu.error` shape with matching requestId and `code=CONFLICT` (Go producer: `server/apps/app-api/internal/doudizhuapi/realtime.go`, `realtimeErrorEnvelope`). Expected: promptly settle that command with the known rejection/code and clean its timer. Actual: only a notice is emitted; the Promise stays pending until 15s and becomes an ambiguous timeout. Impact: wrong retry/error semantics and unnecessarily retained requests. Fix direction: strictly correlate and settle error replies, preserving genuine response-loss unknown outcomes. Second adversarial test.
- **P2-02 — Terminal action guard is bypassed by the actual submission API.** Location: `GameClientShell.ts:124-127`. Reproduce: apply a COMPLETED snapshot, confirm `hand.canSubmit === false`, then call `submitCommand` with `hand.pass`. Expected: reject before sending. Actual: one command is sent because only connection status is checked. Server authority still prevents an invalid game transition; this is a client gating defect. Fix direction: check hand identity and phase/command eligibility at the submission boundary, while keeping future room-command readiness explicit. Third adversarial test.
- **P2-03 — Supposedly strict private-view parsing accepts impossible/incorrectly typed state.** Location: `clients/packages/doudizhu-client/src/view.ts:32-56`. Reproduce with the valid-version fixture: duplicate a seat position, or use `cards=['ZZ','ZZ']` and string `playingSeat='attacker-seat'`. Expected: reject malformed data before exposing a typed authoritative projection/readiness. Actual: both variants pass and are cast to `PrivateHandProjection`; seat uniqueness, card identity/uniqueness and optional numeric seat fields are not validated. Impact: invalid client views and misleading action readiness; no server-authorization bypass was demonstrated. Fix direction: validate the actual Go projection's required/optional field types and structural invariants without duplicating game rules. Fourth/fifth adversarial tests.
- **P2-04 — No outstanding-command capacity bound is implemented.** Location: `GameClientShell.ts:127-133`. Reproduce: while connected, submit 1000 distinct requestIds with a socket that sends successfully but never acknowledges. Expected: an explicit finite pending limit/backpressure policy rejects excess work before registering more timers. Actual: all 1000 are sent and retained; the only admission check is duplicate ID. The 15s timeout bounds lifetime but not peak entries under an arbitrary submission rate. Impact: avoidable client memory/work growth; normal disposal does clean the tested burst. Fix direction: define and enforce a pending-count/queue budget, with capacity released on every terminal path. See the baseline JSON/probe. No production concurrency/capacity promise is inferred from its timings.

No P0 or P3 finding was established. Positive fault controls passed: unrelated-hand/stale snapshots did not replace confirmed state; duplicate/reordered replies remained correlated; response loss retained unknown-outcome semantics and same-ID retry; reveal was refused before transmission when server AAD context was missing.
