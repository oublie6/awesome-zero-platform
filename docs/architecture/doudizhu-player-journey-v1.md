# 斗地主玩家体验与公平验证 — 交互设计 v1

> 2026-11-22 设计决议。**本文件同时标注已经具备的能力与尚未交付的交互目标；不把 UI 设计当作已验收功能。**

## 目标与归属

- **所有者**：Cocos 游戏呈现层（微信小游戏、Web 等统一使用）；Vue Web 仅负责网站入口、平台账号登录/注册/账号设置及装载同源游戏框架。
- **目标**：用户只需“创建房间、加入房间、继续已有游戏”，之后仅展示当前阶段真正需要的操作。避免重复大厅和开发工具式按钮菜单。
- **服务端权威**：Go 授权房间成员和 seat、负责公平贡献托管、洗牌、叫分、出牌、截止时间、终局与不可变归档。UI 不自行确定房主、开始资格、牌局结果或恢复成功。
- **依赖**：维持当前 Vue → same-origin Cocos frame 会话通知；Cocos 从现有授权 HTTP/WSS 协议获取 room、fairness、hand 和 final evidence，复用现有客户端协调器。任何房间号、Player AccountID、随机字符串不得成为可冒充的权限证明。
- **安全/资源**：不把验证字符串、手牌、会话令牌、房间私有视图缓存到本地；输入只活在本次授权目的与场景，账号/房间/牌局/用途改变即清除。重复请求、UNKNOWN、ACK 丢失、COMMIT 歧义沿用现有精确 requestId/sequence 核对机制，**不能靠自动重复发送新命令消除异常**。

## 唯一玩家流程

1. **登录**：Web 在 Vue 登录；微信在 Cocos/平台身份组件登录；进入统一 Cocos 大厅。会话恢复仅调用服务端验证。
2. **未加入房间**：两个主动作“创建房间”“加入房间”（输入房间号）。发现未完成的授权房间时可“继续游戏”；只有一个明确可恢复目标时现有协调器可自动恢复；多个目标则用户选择，不能猜。
3. **房间等待**：三张 seat 状态卡，房间号可读。本人未准备时只有“准备”；已准备则等待，全部准备且有资格时可“开始游戏”；保留刷新/退出等低优先级操作。
4. **公平贡献**：新局需要本人参与时才显示“输入本人验证字符串”“提交”。成功仅以服务端确认和重新查询为准；提交后不再在客户端保存该字符串；等待其他参与者或服务端信标时显示状态，不显示多步技术操作。历史 legacy hand 的 recovery kit 工具必须保留在“更多”而不伪装成新局流程。
5. **牌局**：直接显示已经验收的 Cocos 桌面，叫地主/出牌/Pass/倒计时、UNKNOWN 核对保持原语义；游戏过程不得提前揭示他人手牌、可推导洗牌的材料。
6. **结算**：先展示输赢/分数，主动作“再来一局/返回房间”（在现有服务端能力支持时启用），次动作“公平验证”。具体动作需依据权威房间状态判断，不伪造一键重开。
7. **历史对局**：长期目标是在单独的历史页面通过账号授权、分页查询已归档牌局并打开对应公平验证。当前代码支持已知 handId 的最终证据获取，但**尚无已验收的跨房间完整历史列表 API**；在该 API 真正交付之前，只能提供本房间最近一局/已知归档的验证，不展示假的历史记录。

## 公平验证产品规则

- **进行中**：只显示公平承诺与贡献状态；不发布使隐藏牌可以被提前预测的材料。
- **归档后**：已存在的 FinalEvidence/已归档证明、个人贡献加密托管记录及本人的字符串核对接口可用。验证界面分为易读结果和技术详情，技术详情包含可公开的承诺、信标、洗牌/发牌与行动摘要，但不得超出 API 已实际公开并验证的数据。
- **必须区分结算已归档与独立验算通过**：服务器返回“已归档”不等于客户端独立重算了所有洗牌和出牌证明。个人字符串匹配也不能代替全部牌局公平性证明；未运行的验证步骤显示“未验证/暂不支持”，而非 PASS。
- 用户本人字符串只能主动输入/验证；输入不落盘、不发日志、不跨账号/牌局/目的保留。

## 状态驱动操作规则

| 服务端已验证的场景 | 主操作 | 次操作/异常 |
| --- | --- | --- |
| 无登录会话 | 登录/绑定 | 注册在账号入口 |
| 无房间 | 创建、加入 | 授权发现/恢复、帮助 |
| 房间尚未完成授权查询 | 同步房间 | 不允许准备/开始/创建新命令 |
| 等待人员或准备 | 未准备者可准备；全部准备按服务端限制开始 | 查看三个座位、同步、退出 |
| 新局提交本人贡献 | 提交本人验证字符串 | 只在原请求 UNKNOWN 时精确核对 |
| 等待其它贡献/信标 | 同步进度 | 不再重复提交 |
| 已知 BIDDING/PLAYING | 进入已确认牌桌 | 同步 |
| 本房间已有已归档牌局 | 查看公平验证 | 本人终局字符串核对 |
| Room 命令 UNKNOWN | 核对原房间命令 | **隐藏新的不可逆房间操作** |
| Fairness 命令 UNKNOWN | 核对原贡献命令 | 不重复提交新贡献 |
| 旧局 legacy 贡献流程 | 明示“旧局恢复工具” | 不能用新局简单流程代替 |

## 迁移阶段

**第一阶段（本轮实现）**：
- Vue 登录后只提供一个“进入游戏大厅”入口，不再重复铺设创建/加入/恢复三卡片，保留原同源通信安全约束。
- Cocos 将主菜单改为按授权状态投影，并展示三席位信息；次级“更多”保留同步、恢复、账号绑定和旧局工具。
- 区分加入房间号、开局贡献字符串与终局核对字符串的瞬时输入目的，修正 UNKNOWN 时的菜单收敛；已归档本局的公平验证入口保留。
- 添加入门场景状态组合测试、账号/房间/手牌/输入用途隔离测试、现有协议与构建回归。

**下一阶段（需继续开发和独立验收）**：
- 真正的图片/动画化座位卡、复制房间号/跨端分享、结算页“再来一局”、跨房间历史对局列表与独立验算详情。
- 新的独立历史列表/分享协议需要单独版本化 API、成员鉴权/分页/隐私与验收，不能以纯前端数据拼接代替。
- Web Cocos 真机/低端设备、首次加载性能及无障碍测试。

## 迁移与回滚

该阶段只调整前端显示与导航，不迁移 MySQL、队列、账号/回合/公平证明协议，不改已部署 Kubernetes；部署前由 Codex 对固定 SHA 独立验收。回滚为恢复先前 Vue/Cocos 静态镜像，不涉及历史数据或服务端 DQ 切换。不得在旧前端会话仍有 UNKNOWN 时擅自转换请求身份。

## 验收与指标

- 两个大厅的“创建/加入/恢复”重复入口从 Vue 移除；Cocos 无房间主动作不超过 2 个、已验证房间主动作通常 1 个。
- 对未授权/旧身份/未验证房间隐藏写操作；房间/公平 UNKNOWN 时仅显示精确核对；没有错误的“一键成功”。
- 已知三个座位可显示，旧局工具只在适用时可达。本人贡献/终局核对的输入不会跨目的或账号复用。
- 真实 Web/WeChat Cocos 导出、窄横屏/竖屏触摸及权威恢复的结论必须由后续 Codex/真机证据单独提供，不以静态测试代替。
